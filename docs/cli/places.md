# 駅・バス停の検索と位置情報

`search` で候補を探し、`subway station` で地下鉄駅の基本情報、`coordinates` で代表座標、`nearby` で周辺の交通施設を調べられます。対象は名古屋市バス停と名古屋市地下鉄駅です。端末のGPSや利用者の現在位置は取得しません。

## 地点種別と完全修飾名

地点種別は市バスが `bus`、地下鉄が `subway` です。同名でも別の交通施設として扱います。完全修飾名は、名前に交通機関を付けた `藤が丘(名古屋市地下鉄)`、`藤が丘(名古屋市バス)` の形式です。

通常名は前後空白除去・NFKC正規化後に完全一致、部分一致の順で解決します。完全修飾名は正規化後の完全一致だけで解決し、似た名前の別施設へ読み替えません。候補が複数なら自動選択せず、`ambiguous` と終了コード3を返します。候補なしは `not_found` と終了コード3です。

検索結果の `qualified_name` は `route`、`subway station/timetable/next`、`bus stop/timetable/live`、`fare`、`pass`、`coordinates`、`nearby` の地点引数へそのまま渡せます。地下鉄専用コマンドと料金検索には地下鉄、市バス専用コマンドには市バスの候補を選んでください。種別が矛盾する入力は `invalid_arguments`（終了コード2）です。駅記号は表示用で、地点入力には施設名か完全修飾名を使います。内部IDをコマンド間で受け渡す必要はありません。

Humanの「入力用」や再実行例はbash・zsh向けに引用符を付けます。JSONの `qualified_name` は引用符を含まない値です。ほかのシェルでは、そのシェルの引数の引用方法に合わせてください。ハイフンで始まる施設名は `--` の後に指定し、オプションはその前に置きます。

完全修飾名の種別と `coordinates --type`、`nearby --origin-type` が矛盾すると、通信前に `invalid_arguments` と終了コード2を返します。`nearby --result-type` は検索結果の種別であり、基準地点とは独立しています。

## 名前から探す: search

```sh
nkotsu search 藤が丘
nkotsu search 藤が丘 --type subway --limit 5 --json
nkotsu search 上社 --type bus
```

`--type bus/subway` の省略時は両種別を検索します。`--limit N` は1以上で、既定20件です。空文字・空白だけの検索語は、通信前に引数エラーとして拒否します。

JSONの `data` は `query`、`retrieved_count`、`results` を持ちます。`query` は正規化した検索語、`retrieved_count` は重複排除後・件数制限前の取得済み候補数です。上流データ全体の件数を保証しません。候補は次の項目を持ちます。

| 項目 | 内容 |
| --- | --- |
| `name` / `qualified_name` / `type` | 施設名・完全修飾名・地点種別 |
| `codes` | 地下鉄の駅記号。市バスは空配列 |
| `reported_lines` | 取得できた路線・系統名。所属路線を網羅する一覧ではない |
| `latitude` / `longitude` | 取得した座標。情報なしや不正な場合は両方 `null` |

正規化した名前が検索語と完全一致する候補を先にし、その後は名前・種別・完全修飾名順に並べます。推薦順位ではありません。件数制限は重複排除・ソート後に適用します。有効な検索で0件なら成功です。

片方の種別だけ取得に失敗した場合は、他方の候補と失敗情報を返します。単一種別を指定した検索の取得失敗、両種別の取得失敗は全体失敗で `data: null` です。座標の不正・矛盾では候補を保持し、座標だけを `null` にして部分失敗とします。名前・識別子・種別が不正な候補は除外し、正常な候補を残します。

Human表示は取得済み候補数と表示件数を示します。部分結果の件数は取得できた範囲だけです。候補には名前、種別、「駅記号」「参考路線・系統」、引用符付きの入力用完全修飾名を表示します。参考路線・系統は所属路線を網羅しません。座標は `coordinates` で確認してください。サジェストののりば情報は公開しません。乗車するホーム・のりばには、既存の `bus stop` や時刻表を使います。

## 地下鉄駅の基本情報: subway station

```sh
nkotsu subway station 藤が丘
nkotsu subway station '名古屋(名古屋市地下鉄)' --json
```

JSONの `data` は `name`、`qualified_name`、`codes`、`latitude`、`longitude` を持ちます。時刻表用駅IDは公開しません。Human表示では駅記号を `H08 / S02` のように区切り、座標なしは「不明」とします。市バス停の詳細には `bus stop` を使ってください。

駅マスターを取得・解析できなければ全体失敗です。駅を解決した後の座標取得・解析失敗や、その駅の座標の不正・矛盾では、駅名と駅記号を保持して両座標を `null` にし、部分失敗を返します。正常に取得したデータにその駅の座標がなければ、正常な `null` とします。

## 代表座標: coordinates

```sh
nkotsu coordinates '藤が丘(名古屋市地下鉄)'
nkotsu coordinates 藤が丘 --type subway
nkotsu coordinates 上社 --type bus --json
```

`--type bus/subway` で地点種別を絞れます。JSONの `data` は `name`、`qualified_name`、`type`、`latitude`、`longitude` を持ちます。Human表示には名前、種別、緯度、経度を含めます。

座標マスターと市バス・地下鉄の名前マスターを使います。3マスターのどれかを取得・全体解析できなければ全体失敗です。座標が欠落・不正でも名前の候補には残し、別の同名施設へ読み替えません。選択した施設に有効な座標がなければ `invalid_response` と終了コード5を返します。無関係な施設の座標異常だけでは失敗しません。

## 周辺の交通施設: nearby

```sh
nkotsu nearby '藤が丘(名古屋市地下鉄)'
nkotsu nearby 藤が丘 --origin-type subway --result-type bus
nkotsu nearby 栄 --origin-type subway --radius 500 --limit 5 --json
```

| オプション | 内容 |
| --- | --- |
| `--origin-type bus/subway` | 基準地点の種別 |
| `--result-type bus/subway` | 探す施設の種別 |
| `--radius METERS` | 最大概算直線距離。1以上、既定1,000m |
| `--no-radius` | 距離制限なしで近い順。`--radius` と同時指定不可 |
| `--limit N` | 最大表示件数。1以上、既定10件 |

基準地点は `coordinates` と同じ規則で解決します。基準地点自身を除外し、結果の種別、半径、距離順、件数の順で絞ります。同名でも種別が違う施設は残します。

距離は交通施設の代表点の緯度・経度からHaversine式で求める概算直線距離です。入口・のりば間の距離とは限りません。同じ代表座標や整数への丸めで0mになることがありますが、同一施設・直接乗換可能・実際の移動距離0mを意味しません。徒歩・道路の距離や移動時間を意味しません。半径は丸め前の距離で判定し、たとえば500.4mは半径500mに含めません。公開値 `distance_m` はメートル単位へ四捨五入した整数です。この整数の昇順、同じ値なら完全修飾名順に並べます。

JSONの `data.origin` は `coordinates` と同じ項目です。`data.places` は各候補の同じ項目に `distance_m` を加えた配列です。`data.matched_count` は有効施設から基準施設を除外し、結果種別・半径を適用した後、件数制限前の候補数です。部分結果では取得できた範囲だけを数えます。Human表示は基準施設・有効な半径・結果種別、候補数と表示件数、名前・種別・距離・入力用完全修飾名を示します。省略した候補があるときは `--limit` を増やす実行例を添えます。座標が必要ならJSONまたは `coordinates` を使ってください。

3マスターの取得・全体解析失敗、基準地点の座標欠落・不正は全体失敗です。検索対象種別の不正地点は除外し、正常な候補を保持して部分失敗とします。座標不明の地点は半径内か判定できないため、半径や件数制限でエラーを隠しません。完全な取得・検証で0件なら、実際の `origin` と `places: []` を返して正常終了します。

## 座標と対象施設の境界

座標は有限値と範囲（緯度−90〜90、経度−180〜180）を検証します。不正値を `0,0` や平均値で補いません。`search`・`subway station` では両座標の欠落は正常な `null`、片方だけの欠落・不正値・矛盾は部分失敗です。

市バスとして登録された施設は、ゆとりーとライン関連の路線名があっても市バス側を対象に含めます。「(ゆとりーとライン)」や「あおなみ線」の別施設レコードは対象外であり、同じ座標でも統合しません。

## キャッシュ・raw・終了コード

`search` は永続キャッシュせず毎回取得します。`subway station`・`coordinates`・`nearby` のマスターはHTTPの鮮度指示に従って保存し、指定がなければ24時間を既定とします。`--refresh` と `--no-cache` は既存の規則を使います。

`--raw` は取得URL別に元の本文を文字列で返し、BOM・空白・改行を保持します。検索は最大2URL、駅情報は最大2URL、位置・周辺検索は3マスターを取得します。同一URLは1回だけです。

JSONは既存の `schema_version: 1`、`complete`、`data`、`errors` のEnvelopeを使います。部分失敗は `complete: false` と非0終了コードを返します。共通の出力・終了コードは `nkotsu docs show output`、エラーへの対処は `nkotsu docs show troubleshooting` を参照してください。

## エラー・0件から続ける

地点名が曖昧なら、Humanの候補ごとの再実行例を選べます。元の日時・半径・件数などの条件を保持し、今回曖昧だった引数だけを置き換えます。JSONでは `errors[].candidates` に `name`、`qualified_name`、`type` を持つ候補を返します。経路・料金検索の地点解決では `route.from`、`route.to`、`route.via`、`fare.from/to`、`pass.from/to` の `scope` で修正対象を区別します。正規化すると候補の完全修飾名まで同一になる場合はデータ上区別できず、再実行で解決するとは案内しません。

未発見では無関係な施設一覧を候補として出さず、入力した名前と種別を使う `search` の実行例を示します。検索成功や候補の存在を保証する案内ではありません。

正常な周辺0件では、有効な条件を確認し、表示される距離制限解除や結果種別解除の再検索例を使えます。すでに無制限なら距離制限解除、種別未指定なら種別解除は案内しません。すべての絞り込みを外しても0件なら、取得した対象データの範囲に候補がありません。

部分結果はHumanの冒頭に「部分結果」と不足・不正な範囲を表示し、非0で終了します。`--quiet` でもこの表示を残し、詳細はstderrへ出します。不完全な0件は全範囲の該当なしと断定しません。

選択した施設の座標を使えない場合は、施設自体は見つかったことと座標の欠落・不正を区別して示します。`subway station` または `bus stop` の案内は基本情報の確認用で、座標の問題を解消するものではありません。

## 初期v0.3.0設計・実装からの変更

| 旧仕様 | 現在の仕様・移行方法 |
| --- | --- |
| `nkotsu location <PLACE>` | `nkotsu coordinates <PLACE>` |
| `nkotsu station <STATION>` | `nkotsu subway station <STATION>` |
| `nearby --type TYPE` | `nearby --result-type TYPE`。`search`・`coordinates` の `--type` は維持 |
| 検索結果の `total` | `retrieved_count`。取得済み有効候補数、件数制限前 |
| 検索候補の `lines` | `reported_lines`。取得できた参考路線・系統のみ |
| `nearby` の半径省略で無制限 | 既定1,000m。無制限にするには `--no-radius` |
| `nearby` の表示件数だけ | `matched_count` で条件内の取得済み候補数も取得可能 |

旧コマンド名・旧オプション名の互換エイリアスはありません。実行例やスクリプトを書き換えてください。JSONの座標結果はタグなしの同じ構造を維持し、新しい `coordinates` キーは追加しません。

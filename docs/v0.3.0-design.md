# v0.3.0 設計: 駅・バス停の検索と位置情報

初期設計の13項目と設計全体は2026-10-05に確認し、実装・バージョン更新をコミット `a494236` に記録した（この実装の座標コマンド名は `location`）。CLI利用者目線のUX改訂12項目と設計全体（UX-Q13）は2026-10-05に確認済み。追加UX8項目、旧コマンド名の廃止、`Data::Coordinates` への改名を含むUX改訂全体も、追加UX-Q12（A）で2026-10-05に最終確認済み。以下のUX確定事項は設計変更であり、実装への反映は未実施。

## 目的と対象

テーマは Place Discovery とする。名古屋市交通局の駅・バス停を名前から探し、同名施設を区別し、位置関係を調べられるようにする。

対象は名古屋市バス停（`bus`）と名古屋市地下鉄駅（`subway`）。観光スポット、住所、店舗、ATM、駅設備、他社交通機関は含めない。

**Q13確定: 市バス施設への登録と、同じ場所にある他社交通の施設を区別する。** ゆとりーとライン関連の地点でも、市バスマスターと座標マスターの「(名古屋市バス)」側に登録された施設は `bus` として含める。関連する路線名が検索で返っても、その名前だけを理由に市バス側の施設を除外しない。「(ゆとりーとライン)」の別レコードは対象外とし、同じ座標でも市バス側へ統合しない。名前マスターに登録された施設の座標が欠落した場合に候補を保持するQ2の規則は変えない。[ADR-0009](adr/0009-discover-registered-city-bus-facilities.md) に理由を記録する。

v0.1.0・v0.2.0のコマンド、JSON Envelope、終了コード、キャッシュ、`--raw`、内蔵docsの基本設計を維持する。`schema_version` は数値の `1` のままとし、既存の `model::Place` の非公開フィールドを公開しない。

## コマンド

| コマンド | 用途 | 引数・オプション |
| --- | --- | --- |
| `search` | 駅・バス停の横断検索 | `<QUERY>`、`--type bus/subway`、`--limit N`（既定20） |
| `subway station` | 地下鉄駅の基本情報 | `<STATION>` |
| `coordinates` | 駅・バス停の代表座標 | `<PLACE>`、`--type bus/subway` |
| `nearby` | 基準地点の周辺にある駅・バス停 | `<PLACE>`、`--origin-type bus/subway`、`--result-type bus/subway`、`--radius METERS`（既定1000）、`--no-radius`、`--limit N`（既定10） |

件数・半径は1以上。`nearby` の半径省略時は1,000mとし、距離制限なしは `--no-radius` で明示する。`--radius` と `--no-radius` は同時指定できない。既存のグローバルオプションを利用できる。

## 旧コマンド名との互換性

**追加UX-Q10確定（B）:** 座標コマンドの正式名は `coordinates`、地下鉄駅情報の正式名は `subway station` とする。旧名の `location`・トップレベル `station` は廃止し、互換エイリアスは設けない。新しいhelp・実行例・利用者向けSkillは正式名に統一する。

変更一覧に `nkotsu location <PLACE>` → `nkotsu coordinates <PLACE>`、`nkotsu station <STATION>` → `nkotsu subway station <STATION>` の移行方法を記載する。旧名を使った実行例やスクリプトには書き換えが必要になることを明記する。この決定はコマンド名の互換性方針であり、Data variantの名称は追加UX-Q11に従う。

## 名前と地点種別

完全修飾名は `藤が丘(名古屋市地下鉄)`、`藤が丘(名古屋市バス)` の形式とし、公開フィールド名を `qualified_name` とする。コマンド間で内部IDを受け渡さない。

**UX-Q1確定（A、初期Q7を変更）: 完全修飾名を関連コマンド共通の入力にする。** `search` の `qualified_name` は `route`、`subway station`、`coordinates`、`nearby` に加え、`bus stop/timetable/live`、`subway timetable/next`、`fare`、`pass` の地点引数へそのまま渡せる。通常の名前入力も維持する。コマンドの対象種別と完全修飾名の種別が矛盾する場合は、読み替えず `invalid_arguments`（終了コード2）で拒否する。検索後に `name` へ戻す使い分けを要求しない。これは入力仕様の拡張であり、既存のJSON出力の変更は求めない。[ADR-0010](adr/0010-reuse-qualified-names-across-place-commands.md) に理由を記録する。

**追加UX-Q1確定（A）: 通常名による探索と、完全修飾名による施設指定を分ける。** 地点引数の通常名は前後空白除去、NFKC正規化、完全一致、部分一致の順で解決する。完全修飾名は前後空白除去・NFKC正規化後の完全一致だけで解決し、部分一致へ進まない。これは完全修飾名を受理する関連コマンドすべてに適用する。完全一致が複数でも自動選択せず `ambiguous`（終了コード3）、候補なしは `not_found`（終了コード3）を返す。完全修飾名が見つからなくても似た名前の別施設へ読み替えない。曖昧な施設を自動選択しない方針は [ADR-0003](adr/0003-reject-ambiguous-endpoint-names.md) を維持し、完全修飾名の共通入力と厳密な施設指定は [ADR-0010](adr/0010-reuse-qualified-names-across-place-commands.md) に記録する。

**UX-Q4確定（A）: 曖昧な名前から直接再実行できる案内を返す。** Humanの曖昧性エラーは候補を一件ずつ表示し、完全修飾名を指定したコピー可能な再実行コマンドを添える。元のコマンドと、半径・件数・結果種別・日時など利用者が指定した条件を保持し、曖昧な地点引数だけを候補に置き換える。複数地点引数があるコマンドでも、今回判定できた候補の案内で未解決の他地点を勝手に選ばない。候補が既に分かっている場合は、再度 `search` を実行することを必須にしない。終了コードと自動選択しない方針は維持する。

CLI内部の地点種別は `PlaceType::{Bus, Subway}`。CLI・JSONでは `bus` / `subway`、Human表示では「市バス」/「地下鉄」とする。種別を指定するhelpでは `bus（市バス）` / `subway（地下鉄）` の対応を明記し、実行例にはCLIが受理する値を使用する。完全修飾名の交通機関名は「名古屋市バス」「名古屋市地下鉄」を維持する。

**Q5確定: 完全修飾名と明示した種別が矛盾する場合は引数エラーにする。** `coordinates '藤が丘(名古屋市地下鉄)' --type bus` と、同じ完全修飾名に `nearby --origin-type bus` を指定した場合は、API取得前に `invalid_arguments`（終了コード2）を返す。種別を読み替えず、施設が存在しない `not_found` とも区別する。`nearby --result-type` は結果の種別を指定するため、基準地点の種別と異なっていても矛盾とは扱わない。

## 駅記号と地点入力

**追加UX-Q8確定（A）:** 地下鉄の駅記号は表示情報とし、駅記号を地点名へ変換する入力仕様は追加しない。関連コマンドのhelp・docsに、地点入力は施設名または完全修飾名であることを明記する。`H22` 等を表示しても、その値を `subway station`・時刻表・経路・料金・座標・周辺検索の地点引数として受理するとは説明しない。

`search` の上流APIが駅記号の検索語を受理するかは未確認であり、駅記号検索をサポートするとは案内しない。完全修飾名の共通入力を優先し、駅記号による指定を広げる場合は別途設計する。

## 地点の種別と経路の交通手段

**追加UX-Q7確定（A）:** `route` の完全修飾名は出発・到着・経由の交通施設を指定するもので、経路全体の利用交通手段を制限しない。地下鉄だけの経路を要求する場合は `--subway` を使う。この違いをhelp・docsに明記し、地下鉄の完全修飾名と `--subway` を組み合わせた実行例を示す。

Human結果には実際の検索条件に基づき「検索対象の交通手段: 地下鉄のみ」「検索対象の交通手段: 市バスのみ」「検索対象の交通手段: 市バス・地下鉄」のいずれかを表示する。これは許可した交通手段を示し、全種別を必ず利用するという意味ではない。既存の交通手段指定の挙動は維持する。

## 未発見の地点からの復帰

**追加UX-Q3確定（A）:** 地点名の `not_found` エラーでは、マスター先頭の無関係な施設一覧を「候補」として表示しない。入力した通常名を使った `search` のコピー可能な実行例を案内し、地点の指定済み種別があれば `--type` に反映する。完全修飾名の場合は交通機関接尾辞を外した施設名を検索語とし、接尾辞の種別を検索条件に反映する。

この案内は名前を確認する次の操作であり、検索成功や候補の存在を保証しない。入力に似た施設を推測で自動選択せず、曖昧性エラーの既知候補とも区別する。

## JSONの曖昧性からの復帰

**追加UX-Q2確定（A）:** 地点名の `ambiguous` エラーには構造化した `candidates` 配列を追加する。各候補は `name`、`qualified_name`、`type`（`bus` / `subway`）を持つ。Agentは `message` の文章を解析せずに候補を取り出し、選んだ `qualified_name` を関連コマンドの地点引数へ渡せる。`scope`・`code`・`exit_code`・`message` の既存項目は維持する。

候補情報はHumanの候補案内と同じ施設を示す。内部IDや推測した座標は含めない。この追加は地点名の曖昧性を対象とし、券種や路線など交通施設ではない候補へ施設用フィールドを当てはめない。JSONの既存成功結果を変更せず、地点名の曖昧性エラーに候補情報を追加する。

## 公開モデル

既存の `Data` に `Search`、`Station`、`Coordinates`、`Nearby` を追加する。既存variantの構造は変更しない。座標結果のvariant名は `Data::Coordinates(PlaceLocation)` とし、初期実装の `Data::Location` から改名する。`Data` はタグなしでシリアライズするため、このvariant名はJSONに現れず、新しい `coordinates` キーやタグを追加しない。共通モデル `PlaceLocation` は維持する。

| モデル | 公開フィールド |
| --- | --- |
| `PlaceLocation` | `name: String`、`qualified_name: String`、`type: String`、`latitude: f64`、`longitude: f64` |
| `SearchResult` | `query: String`、`retrieved_count: usize`、`results: Vec<SearchPlace>` |
| `SearchPlace` | `name: String`、`qualified_name: String`、`type: String`、`codes: Vec<String>`、`reported_lines: Vec<String>`、`latitude: Option<f64>`、`longitude: Option<f64>` |
| `StationInfo` | `name: String`、`qualified_name: String`、`codes: Vec<String>`、`latitude: Option<f64>`、`longitude: Option<f64>` |
| `NearbyResult` | `origin: PlaceLocation`、`matched_count: usize`、`places: Vec<NearbyPlace>` |
| `NearbyPlace` | `PlaceLocation` と同じ公開項目に `distance_m: u32` を追加 |

Rustの `kind` フィールドは `serde(rename = "type")` で公開する。検索APIの `station_cd` と時刻表用駅IDは、新しい公開モデルに含めない。

## search

`GET /optimizeapi/api/Suggest/StationInfos/json` を使う。クエリは `key=<QUERY>`、`marge=pole`、`next=`。`marge` は上流の表記を維持する。

市バスは `div=1`、地下鉄は `div=2`。両種別の検索では別々に取得し、`div=1,2` に依存しない。空文字や空白だけのクエリは正規化後に拒否し、APIを呼ばず `invalid_arguments`（終了コード2）とする。

同じ `station_div` と `station_cd` のレコードを一つの候補にまとめる。駅記号はQ11、路線名はQ12に従って集約する。`pole_name` は公開しない。実際のホーム・のりばは既存の停留所情報・時刻表で確認する。

**Q11確定: 市バスの内部番号と地下鉄の駅記号を区別する。** 市バスの `station_num` は内部停留所番号なので公開せず、`codes: []` とする。地下鉄の同フィールドは `|` で分割し、空要素除去・重複排除した駅記号を `codes` に入れる。たとえば `H08|S02` は `["H08", "S02"]` とする。同一候補の複数レコードについても駅記号を集約する。

**Q12確定: 検索の路線名は取得値に限定する。** `line_name` をカンマで分割し、空要素除去・重複排除した取得値を `reported_lines` に入れる。同一候補の複数レコードも集約するが、別データから補完せず、路線名の表記を推測で読み替えない。この配列は所属路線を網羅する一覧ではない。名古屋の `station_num` が `H08|S02` でも `line_name` が東山線だけの場合は、`reported_lines: ["東山線"]` とする。help・内蔵docs等でも網羅性を保証しない。

**Q10確定: 識別に必要な項目が不正な候補だけを除外する。** 名前・内部ID・種別の欠落や不正は `invalid_response` の部分失敗として記録し、正常な候補を保持する。同じ `station_div`・`station_cd` に異なる名前が付いている場合も、その識別子の候補を除外する。JSON配列自体は解析できても全候補が不正な場合は、`results: []` とエラーを返し、正常な0件や `data: null` に置き換えない。JSON全体の取得・解析失敗には、単一種別の全体失敗、一方だけ失敗した場合の部分結果、Q9の両種別失敗を適用する。

並び順は、正規化した名前がクエリと完全一致する候補を先にし、その後は名前、種別、完全修飾名の順とする。推薦順位とは扱わない。重複排除・ソート後に `--limit` を適用し、`retrieved_count` は適用前の取得済み候補数とする。

一方の種別の取得失敗では、他方の候補を保持し、`search.bus` / `search.subway` のエラーを返す。明示した単一種別の取得失敗はコマンド全体の失敗とする。部分失敗の非0終了は [ADR-0004](adr/0004-report-partial-results-as-errors.md) に従う。

**Q9確定: 両種別の取得が失敗した場合は `data: null` とする。** 市バス・地下鉄とも取得またはJSON全体の解析に失敗した場合は、コマンド全体の失敗として `complete: false`、`data: null` を返し、`search.bus` と `search.subway` の両エラーを保持する。終了コードは既存規則どおり最大値で集約する。一方が正常な0件で他方が失敗した場合は、正常に取得できた検索があるため `SearchResult` を保持し、`retrieved_count: 0`、`results: []` の部分結果とする。

同一候補の座標が矛盾する場合は平均せず、緯度・経度を両方 `null` にして部分失敗を記録する。候補そのものは保持する。座標の両方欠落と、片方欠落・不正値の区別はQ4の規則に従う。

Human表示は冒頭に「取得済み候補N件・表示M件」を示し、件数制限による省略を分かるようにする。部分結果では取得できた範囲の件数であることも明記する。候補には名前、種別、駅記号、参考路線・系統、完全修飾名を表示する。完全修飾名はHumanで「入力用: '施設名(交通機関名)'」のように引用符付きの入力例として表示する。駅記号と路線名をラベルなしで連結せず、それぞれ「駅記号」「参考路線・系統」と表示する。結果内に「参考路線・系統は取得できた情報のみで、所属路線を網羅しません」と明記する。座標は原則表示せず、`coordinates` へ案内する。

## subway station

地下鉄駅専用。市バス停の詳細には `bus stop` を使う。

`/station_data/station_subway_infos/station_master.json` から駅名・駅記号を取得し、`/STATION_DATA/station_infos/station_latlng.json` から代表座標を取得する。

駅マスターの取得失敗は全体失敗。駅を解決した後の座標マスター取得失敗は、駅名・駅記号を保持し、緯度・経度を両方 `null` にして部分失敗とする。座標マスターが正常でも、その駅の座標がなければ推測して補わず、Q4に従って正常な `null` とする。

Human表示は名前、駅記号、緯度、経度。複数駅記号は `H08 / S02` のように区切り、座標なしは「不明」とする。

## coordinates・nearby の地点インデックス

共通の地点インデックスを次のデータから構築する。

| データ | 用途 |
| --- | --- |
| `/STATION_DATA/station_infos/station_latlng.json` | 地点名・緯度・経度 |
| `/station_data/station_infos/station_name.json` | 市バス停名の集合 |
| `/station_data/station_subway_infos/station_master.json` | 地下鉄駅名の集合 |

**Q1確定: 3マスターすべてを必須にする。** いずれかの取得・全体解析が失敗した場合は、`coordinates`・`nearby` のコマンド全体を失敗させる。片方の名前マスターだけでは接尾辞のない名前が両種別に存在するか確認できず、同名施設を誤選択するおそれがあるため、欠けたマスターを空集合として扱わない。

名前に `(名古屋市地下鉄)` / `(名古屋市バス)` が明示されていれば、その種別を使う。接尾辞がなければ、一方の名前マスターだけに存在する場合に分類する。両方に存在する場合は推測せず、該当レコードを除外して `invalid_response` の部分失敗を記録する。どちらにも分類できない他社交通等の地点は対象外として除外する。

`coordinates` は登録された交通施設の代表座標を返し、利用者や端末の現在位置を取得しない。Human表示は「施設名 [種別] の代表座標」を見出しとし、緯度・経度を表示する。

**Q2確定: 座標の欠落・不正で名前の候補を減らさない。** 名前と種別による施設の解決を、座標を返せるかどうかの判定より先に行う。藤が丘の地下鉄座標が不正でも、種別を指定しない藤が丘を同名の市バス停として選ばない。同名施設が複数なら `ambiguous`（終了コード3）を返す。解決した施設に有効な座標がない場合は `invalid_response`（終了コード5）で全体失敗とする。この規則は `coordinates` と `nearby` の基準地点に適用する。名前マスターに施設があっても座標レコードがない場合も含む。[ADR-0008](adr/0008-preserve-place-identity-without-valid-coordinates.md) に理由を記録する。

**Q8確定: 座標マスターの同じ完全修飾名は一つの施設として扱う。** 同じ有効な座標を持つ重複レコードは一つに統合する。座標の矛盾や不正がある場合は、先頭レコード・平均値・別地点扱いで代表座標を決めず、座標を利用できない施設として名前の候補を残す。`coordinates`・`nearby` の基準地点として選択した場合はQ2の全体失敗、`nearby` の検索対象候補ならQ3の部分失敗とする。`subway station` で該当施設の座標が矛盾・不正ならQ4に従って駅情報を保持する。

## nearby

基準地点は `coordinates` と同じ地点インデックスから解決する。同名の市バス停・地下鉄駅がある場合は、`--origin-type` または完全修飾名で区別する。

基準地点自身を除外し、結果の `--result-type`、距離計算、`--radius`、ソート、`--limit` の順に処理する。同名でも種別が違う施設は残す。

**追加UX-Q5確定（A）:** `nearby` のJSONに `matched_count` を追加する。取得済みの有効施設から基準施設を除外し、結果種別・半径条件を適用した後、`--limit` 適用前の件数を返す。Humanには「条件内の取得済み候補: N件 / 表示: M件」と表示し、件数制限で省略した場合だけ `--limit` を増やす案内を添える。部分結果では取得できた範囲の件数であり、上流全体の件数を保証しないことを明記する。

距離は交通施設の代表点の緯度・経度からHaversine式で求める概算直線距離。地球半径は実装内の定数とし、公開値はメートル単位の整数へ丸める。徒歩距離・道路距離・実際の移動距離・所要時間とは扱わない。Human結果に「施設の代表点間の概算直線距離」「入口・のりば間の距離ではありません」と明記する。docsでは、同じ代表座標や整数への丸めにより0mになることがあり、同一施設・直接乗換可能・移動距離0mを意味しないと説明する。

**Q6確定: 半径は丸め前、並び順は丸め後の距離を使う。** `--radius` は丸め前の距離が指定値以下の地点だけを残す。500.4mの地点は半径500mに含めない。その後、メートル単位へ四捨五入した `distance_m` の昇順に並べ、同じ整数距離なら完全修飾名順とする。Human表示とJSONには同じ整数距離を使う。

取得・検証が完全で、有効な条件で0件なら正常終了し、JSONには実際の `origin` と `places: []` を返す。Human表示は「該当する周辺の交通施設はありません」。候補の欠落がある場合は0件でもQ3の部分失敗とする。Humanでは0件の場合も「施設名 [種別] を基準とする周辺施設」と「検索半径: N m / 距離: 施設の代表点間の概算直線距離」を表示する。`--no-radius` の場合は「距離制限なし・近い順」と明記する。候補の名前・種別・距離に加え、引用符付きの入力用完全修飾名を表示する。座標はJSONまたは `coordinates` で確認できるようにする。

## 正常な周辺0件からの復帰

**追加UX-Q4確定（A）:** 完全に取得・検証できた `nearby` の0件結果では、有効な検索半径と結果種別を表示する。条件に応じ、「半径を広げる」「結果種別の条件を外す」のコピー可能な再検索例を提示する。基準施設は完全修飾名を使用し、変更する条件以外の指定は保持する。利用者が候補を探し直せる操作を案内し、再検索で必ず候補が得られるとは説明しない。

`--no-radius` 指定済みなら半径を広げる案内は出さず、結果種別が未指定なら種別条件を外す案内は出さない。変更できる絞り込み条件がなければ、取得した対象データの範囲で0件だったことを説明する。部分失敗の0件にはUX-Q7の不完全な結果の表示を優先し、完全な該当なしと区別する。

## 座標を利用できない施設からの復帰

**UX-Q12確定（A）:** `coordinates`・`nearby` の基準施設が解決済みでも座標を利用できない場合は、Humanエラーに施設名・種別と、施設自体は見つかっていることを示す。座標の欠落なら「代表座標が登録されていません」、不正なら「座標データが不正です」と区別し、要求した座標取得・周辺検索ができない理由を説明する。`invalid_response` と終了コード5は維持する。

続けられる操作として、地下鉄なら `subway station`、市バスなら `bus stop` の完全修飾名を使った実行例を提示する。これらは施設の基本情報を確認する案内であり、座標問題の解消や代表座標の代替取得を保証しない。別の同名施設への読み替えや、のりば座標からの代表座標の推測は行わない。

## 部分失敗のHuman表示

**UX-Q7確定（A）:** 部分失敗は取得済みデータを保持し、既存の非0終了とJSONの `complete: false` を維持する。Humanの結果冒頭に「部分結果」と、未取得・不正な情報の範囲を表示し、どの取得済み情報を表示しているか説明する。詳細エラーはstderrに表示する。`--quiet` でも不完全さを示す表示は省略しない。

`search`・`nearby` 等の部分結果が0件でも「該当する施設はありません」と断定しない。「取得できた範囲では0件。未取得の情報があるため、該当なしとは断定できません」と表示する。正常で完全な0件と、欠落がある0件を区別する。このHuman表示方針をv0.3.0の地点系コマンドに適用する。

## 座標検証とエラー

全座標で有限値を確認し、緯度は−90〜90、経度は−180〜180を受け付ける。不正値を `0,0` などで補完しない。個別レコードの不正と、JSON全体の取得・解析失敗を区別し、候補保持・除外やエラー対象範囲には確定した以下の規則を適用する。

**Q3確定: 個別レコードの異常はコマンドの対象範囲に絞って報告する。** `coordinates` は名前解決した施設の座標を判定し、無関係な施設の座標異常だけで失敗させない。`nearby` は基準地点に加え、結果の種別条件に該当する不正地点を部分失敗として報告する。座標が不明なら半径内かどうかも判定できないため、半径・件数制限の適用前に欠落を記録し、制限によってエラーを隠さない。基準地点自体の座標異常はQ2の全体失敗とする。3マスターの取得・全体解析失敗にはQ1を適用する。

**Q4確定: 任意の座標について、情報なしとデータ異常を区別する。** `search`・`subway station` は緯度・経度が両方欠落している場合、両方を `null` にして正常な結果として扱う。取得した座標マスターに該当駅のレコードがない場合も、この情報なしに含める。片方だけの欠落、不正値、同一施設の座標の矛盾は `invalid_response`（終了コード5）の部分失敗とし、名前・完全修飾名・駅記号等を保持して座標だけを両方 `null` にする。座標が不正でも施設自体は除外しない。マスター全体を取得・解析できなかった状態は、正常な情報なしとは扱わない。

新しいエラーコードは追加しない。`invalid_arguments`、`not_found`、`ambiguous`、`network_error`、`http_error`、`invalid_response`、`parse_error`、`upstream_error`、`cache_error` を使う。Envelopeは [ADR-0005](adr/0005-wrap-normalized-json-results.md) を維持する。

## キャッシュとraw

検索のサジェストは永続キャッシュしない。既存の `Policy::Live` 相当を取得ポリシーとして使い、リアルタイム交通情報を意味する名称として説明しない。

3マスターは `Master` として扱い、既定TTLは24時間。既存のETag、Last-Modified、Cache-Control、`--refresh`、`--no-cache` の規則を維持し、上流の鮮度指示を無視して一律24時間保存する設計にはしない。

`--raw` は取得した本文をURL別の文字列として返す。BOM・空白・改行を保持し、同一URLは1回だけとする。検索は最大2URL、駅情報は駅マスターと座標マスター、位置・周辺検索は地点インデックス用の3マスターを対象とする。

5. **確定（A）:** 完全修飾名と `coordinates --type` / `nearby --origin-type` の矛盾は、API取得前に `invalid_arguments`。`nearby --result-type` は基準地点の種別と独立。

8. **確定（A）:** 同じ完全修飾名・同じ有効座標は統合。矛盾・不正があれば座標を採用せず施設の候補を残し、選択対象に応じて全体失敗・部分失敗とする。
